# Agent execution and credit accounting

Three configurations live inside the same Next.js deployment. Chat, drafting and summary refreshes require explicit invocation. The shared project agent also assesses new shared human Discussion messages and explicitly shared draft copies in the background against accepted terms, as described below. There is no agent-to-agent handoff or background summarisation. Project advice appears to both parties; private advice stays within the invoking party's context. Summaries show their last successful refresh and never become commitments.

Agent questions and published replies use the `agent` message channel and appear inside the appropriate agent-chat panel, including milestone drafting. The main Discussion and engagement-card preview query only the `discussion` channel. A trigger classifies agent-run message references for new/retained responses; migration 27 classifies existing linked exchanges without rewriting their bodies or IDs. Visibility/RLS and retrieval permissions are unchanged; evidence links to agent messages open the scoped agent chat. AI-authored output uses the shared dark-blue text style across chat, summaries, drafting and administrative views.

## Tool inventory and access

### Automatic shared scope/contract assessment

`enqueue_message_assessment` commits one job with each eligible shared message, with an exact accepted-contract/milestone snapshot. Private messages, private files, agent chat, system events and the monitor's own notices are excluded. Accepted milestone scope still works without a Contract; draft/unapproved contracts are never baselines. Messages without accepted terms are visibly skipped, not labelled safe. Existing message history is not retroactively sent to a model.

Next.js `after()` processes a queued job after the human response is sent. The worker retrieves only that shared source, accepted term snapshots and five bounded shared human discussion excerpts. It does not read private material or attachment contents. A single server-side Responses call uses a validated structured schema, no tools, configured model/pricing, no SDK retries, 48 KB input and 1,400 output-token limits. Provider result, service tier, cached-token quantities and actual metering are verified before settlement. Internal provider rates remain server-side.

The claim transaction reserves from the shared account only, caps each reservation at one Workspace token, and limits automatic work to six attempts per author/minute, 60 attempts per engagement/day and five tokens/day (actual successful charges plus outstanding reservations). Private balances are untouched. Failed/unusable/ungrounded/partial results and stale-term checks are platform-funded, with no user charge. Successful checks, including useful no-request/no-conflict classification, settle at the existing internal 2× cost policy; unused reservation is released. One message/operation ID and a locked claim prevent duplicate calls and charges. Low credits, missing setup, budget/rate limits and oversized complete context produce visible skipped states while chat and approval continue working.

Only a potential conflict with an exact source-message substring and an exact quote/reference from an accepted term can publish a neutral shared Discussion reply. The database revalidates grounding and the currently accepted snapshot in the same transaction as settlement/publication. The reply quotes/highlights the request, links its source and the exact accepted version, and explicitly remains advice. Included work, ordinary messages and unclear requests do not receive unsolicited agent replies. No assessment approves amendments, determines legal rights or executes financial actions. Results remain in a member-visible shared assessment record; quiet states appear under the source message.

Either party can pause future automatic checks in Contract. The queue is durable; reopening Discussion resumes queued work. The existing authenticated maintenance endpoint also processes queued work and recovers expired running reservations. Reopening Discussion recovers expired jobs for that engagement. In-flight/uncertain jobs are never automatically rerun; failed checks can be reviewed through the manually invoked project agent. No external queue or always-on scheduler is deployed, so shutdown recovery depends on a later page visit or maintenance invocation. `message_assessments` UPDATE events use member RLS and engagement-filtered Realtime; there are no assessment rows/events for private messages.

Manual agent retrieval includes accepted/latest submitted contracts as explicitly agreed/proposed evidence, with stable version IDs. Contract citations open immutable version history. Long manual-retrieval excerpts are labelled incomplete and cannot supersede their sources.

The Discussion milestone modal invokes shared-only `milestones` mode through the same endpoint and credit pipeline. Its structured milestones contain descriptions only; price/date fields are excluded and the generic proposal/summary fields must be null. No hourly rate is retrieved or required for drafting. People enter completion amounts and target deadlines themselves. The agent uses bounded shared evidence retrieval and must cite the accepted agreement when retrieved. No model response submits or approves a proposal. Partial output remains subject to the existing keep/discard flow inside the project-agent panel. Live provider validation remains pending; deterministic mocks cover the description-only schema and two-call metering path.

For milestone drafting, `milestone_agent_context` supplies up to 20 shared sources before the provider starts: accepted/current proposal versions, recent human Discussion messages and supported extracted shared files. Model-selected search wording does not filter out this context. Prior agent exchanges are excluded to avoid repeatedly retrieving earlier requests or refusals instead of the brief. The existing 30 KB evidence cap still applies, and private material is excluded even when it belongs to the caller. An agreement is not required to draft suggestions from discussion. Empty context returns an actionable error before credit reservation; nonempty milestone suggestions must cite supplied evidence.

The model has one tool: `search_evidence(query)`. It cannot choose an engagement, identity, visibility, model, price, budget or executable action. The authenticated endpoint fixes those from verified membership, environment configuration and immutable pricing. The database independently checks the caller's engagement and role on retrieval. At most one retrieval tool call and one structured answer request execute.

No model tool can approve agreements, rewrite records, publish reviews, submit delivery, schedule binding commitments, pay or refund. All mutations require separate human forms. Copying a private draft requires selecting text, previewing the exact shared copy and confirming. No private history, evidence IDs or activity metadata is automatically copied to shared records.

Retrieval prioritises the exact currently accepted agreement and latest submitted proposal, then relevant authorised messages and extracted text. It returns up to ten sources and a 30 KB evidence budget. Each source includes immutable record/version, visibility, agreed/proposed/discussed state and an excerpt flag. Server validation rejects invented references, changed versions or mismatched visibility. Scope comparisons and summaries must cite the accepted agreement when available. This validates grounding references, not the truth or quality of every generated sentence; human review remains necessary.

Messages are append-only version 1. Attachment text uses the full file's SHA-256 version and stores up to 50,000 characters. TXT/CSV decoding is local, free, signature/UTF-8 checked and marked partial when clipped. PDF/images remain unsupported for agent analysis. Documents, filenames and retrieved text are untrusted data, never permission instructions. There is no URL fetching, code execution, external search, provider file store or vector index.

## Execution limits

The configured model is `gpt-6-luna` at Standard service tier. Versioned rates are $0.10/$0.01/$0.50 per million input/cache-read/output tokens, checked on 2026-11-05. Luna uses explicit-only caching with no breakpoints, disabling caching and cache writes; unexpected or unconfirmed cache usage is rejected. The original pinned `gpt-5-mini-2025-08-07` version remains supported at its recorded $0.25/$0.025/$2 rates. Each run has a 64 KB request cap, 512 retrieval-output tokens, 4096 answer-output tokens (including reasoning), low reasoning effort, two calls maximum, 45-second timeout per call and zero automatic SDK retries. Limits and actual rates determine the server-side reservation; a model configuration without a valid pricing version cannot execute. The Ask action starts a bounded operation without a repeated consent checkbox or browser-supplied charge limit.

The server claims an operation once, then records each provider response once using a unique response ID. Requests use `store:false`. A retry of the same idempotency key returns the saved status/result and cannot execute another model request. Changing the question creates a new key. Individual users are limited to six starts per minute and 200 per day; database limits are capped independently. No raw prompts, private retrieval bodies or credentials are written to console logs.

## Fair billing

USD nanodollars are integers. At the fixed launch conversion, $1 = 10 Workspace tokens and one stored nanodollar equals one hundred-millionth of a token. Existing balances therefore convert exactly without a data rewrite. Input, cached input and output quantities use the immutable rate snapshot. Customer charge = actual verified provider cost × 2; cached inputs are not also billed as uncached inputs. The operation reserves from its own account only, allocating promotional credits before purchased lots. Unused reservations are released. No per-operation cent rounding, negative balances or cross-account borrowing occurs. Provider rates, metering costs and pricing snapshots are server-only; customer usage shows token debits and status.

- Successful usable result: settle actual metered cost × 2 and publish the result atomically.
- Valid usable partial result: hold the quote for up to 24 hours. Only the initiating user can Keep and charge or Discard without charge. Declining/expiry clears the unpublished result and releases the reservation.
- Internal application error, unusable response, invalid structured output/citation, timeout, disconnect with uncertain usage, or cost exceeding the reservation: release customer units; platform absorbs attributable provider expense.
- Provider receipts record known expenses even for failed requests. Uncertain response IDs/usage are marked separately; no estimate is silently charged. Reconcile provider billing operationally. A failure while finalisation status is uncertain tells the user to refresh before retrying rather than promising a charge outcome that has not been confirmed.
- A service-authorised correction reverses a settled charge once, to its original credit sources, retaining the historical charge and receipt. The model cannot issue a correction.

A $5 promotional grant is atomic on a verified account's first engagement creation. Joining a project does not consume eligibility. Private balances start at zero. Shared usage/receipts are shared; private balances, receipts and detailed usage have account-scoped RLS and do not enter shared notifications or summaries. A service-only aggregate promotional-spend report supports monitoring without exposing individual private use.

Credit purchases, supported top-up amounts and refund holds are implemented as transactional records, not working checkout. PayPal verification/capture/webhook wiring is deferred until after the hackathon. A verified admin on the server-only `ADMIN_EMAILS` allowlist can add or remove available promotional demo credits through `/admin`; this creates audit/ledger records, never a fake purchase or provider receipt. Only service-only verified purchase settlement may mark real purchased credits. The platform plans to earn from prepaid AI credits used at 2× attributable provider cost. Direct-to-professional payments carry no Workspace commission. Unused whole-cent purchased credits can be held for a manual refund request, completed only after a verified provider refund. Promotional credits have no cash value; purchased credits have no invented expiration. See ARCHITECTURE.md.

## Recovery and validation status

`POST /api/maintenance` requires a server-held bearer secret (at least 32 characters, timing-safe comparison). It releases up to 100 expired reservations and clears expired partial offers. Running reservations expire after 15 minutes; partial offers after 24 hours. Configure a recurring deployment job; none is installed here. Recovery is safe to repeat. Requests still running after recovery cannot publish or charge against the released reservation.

Deterministic tests cover retrieval privacy, immutable extraction, operation claiming, tool-loop bounds, mocked SDK streaming/metering, citation validation, source allocation, concurrent reservations, refunds/corrections, failed settlement and recovery. Hosted Supabase tests cover actual storage/retrieval privacy and disabled-provider behaviour. The explicitly approved synthetic GPT-6 Luna provider test passed again after removing the AI confirmation payload: two real Responses receipts, evidence citations, no private-context leakage, exact 2× ledger settlement and idempotent replay were verified. The latest run cost $0.0001958 at the provider and charged $0.0003916 (0.003916 Workspace tokens). This smoke test is not a broad assessment of output quality or production reliability. `AI_ENABLED=false` remains the environment-example default; local activation is recorded in PROGRESS.md. No mock result is exposed as a real model response.

Individual milestone versions keep stable `agreement:` evidence references to their immutable source scopes. Retrieval includes current proposed and accepted milestone sources, distinguishes agreed/proposed states, and retains the immutable accepted-set snapshot. Citation links open the exact version archive, including preserved legacy sources. Formal proposal/acceptance event cards are shared Discussion system records; AI drafting exchanges remain in the project-agent channel.

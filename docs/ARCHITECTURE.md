# Architecture, permissions and policies

## Contracts and automatic discussion checks

New engagement creation atomically saves an editable contract draft alongside project funding/starter-grant creation. General freelance services and ongoing-support templates are original starting text, plus a custom option; they make no jurisdiction-specific enforceability or compliance claim. They cover scope/changes, cooperation, acceptance/payment, ownership and pre-existing materials, confidentiality and ending the engagement. Parties must review and adapt them, including any required governing law/forum. Template context references: https://www.business.gov.uk/support/intellectual-property/managing-intellectual-property-working-with-others/ and https://www.creativeworkplaces.gov.au/foundations/essentials/hiring-independent-contractors .

`engagement_contracts` holds draft/latest/accepted pointers. `contract_versions` and `contract_approvals` preserve submitted text and decisions. Submission never approves for either party; two distinct verified members approve the same current proposal under an engagement lock. A new proposal invalidates stale acceptance attempts while retaining the previously accepted contract until both accept a replacement. Contract membership RLS excludes outsiders; account profile types do not confer approval authority. Model tools cannot approve contracts.

Contract is a separate general-terms document; accepted milestones still carry deliverable-specific descriptions, responsibilities, criteria, dates and prices. Ambiguities/conflicts require human agreement. Automatic checks snapshot the exact currently accepted records, never drafts or pending proposals. Source messages commit first; after-response model work is separately reserved, metered and recoverable. See AI.md for budgets, failure billing, retrieval/Realtime isolation and shutdown-recovery limits.

Milestones replaces Overview immediately after Discussion. The shared proposal modal is available in both tabs. It collects description, completion amount (USD), target deadline, required acceptance criteria and optional client responsibilities for each milestone. AI suggests descriptions only. The professional hourly rate is optional profile information and is not required for drafting.

`milestones` owns stable identities and latest/accepted version pointers. `milestone_versions` links each immutable revision to its original scope and task IDs, preserving evidence, delivery and payment references. Submission formally approves only its author’s party; the counterparty accepts that exact current version or proposes an amendment. Either party can propose changes, with a reason required after acceptance. Only submitted edits increment the milestone-local number. Engagement locking and expected-version checks reject competing stale submissions; operation keys make successful retries idempotent. Accepted terms remain in force until the new version has two distinct party approvals; unrelated milestones are unchanged. The separate `milestone_approvals` table isolates approval decisions even when imported tasks shared one original scope. Imported approvals retain their original scope provenance and timestamps; new decisions do not rewrite legacy approvals. RLS and select-only authenticated grants protect every new resource.

Each submission and acceptance atomically creates a structured shared Discussion event and a version-specific link. The Milestones archive is read-only and shows every version, author/time, actual approvals and current/previous acceptance state. Legacy tasks retain their original IDs and scope approvals; tasks across older whole-set revisions are not assumed to be the same milestone. No historical approvals are invented. Historical assumptions/exclusions remain stored but are hidden from this milestone interface.

An immutable accepted-set snapshot contains explicit milestone/version/task references for completion, reputation and agent evidence. It does not manufacture approvals for an aggregate proposal. Delivery/progress authorization checks the individual accepted task, even while another proposal is pending. Accepted delivery/progress controls sit in expandable sections under their milestone. Payment requests keep their original accepted-set/task references; accepting a different milestone does not supersede them. Snapshot prices cannot be charged again as an unallocated balance. Sandbox checkout/refund code is implemented; real provider-backed validation remains pending configuration. Live checkout remains disabled.

The milestone interface has no Gantt, proposed schedule, duplicate plan or synthetic start-date controls. The existing licensed Gantt adapter remains in source for later use; Bryntum Calendar remains integrated. The project-agent composer/history is expandable in Discussion, alongside the latest successful summary. Completion/cancellation is an engagement-header action; eligible feedback appears in Discussion after closure. Old Overview links resolve to Discussion.

Allowlisted, verified administrators have a separate `/admin` path for user records, email confirmation, token adjustments and read-only conversation support. A selected user's shared and party-private messages are displayed separately; the opposing party's private conversation is excluded from that user's view. Reads use server-only service access after an independent admin check and are logged before retrieving messages. Verification requests/completions are recorded in `admin_activity`, which denies ordinary users and permits only service inserts/reads. Admin access grants agents and counterparties no additional visibility. Email confirmation does not imply identity verification.

One TypeScript Next.js app handles SSR, server actions and Supabase access. PostgreSQL functions own atomic grant/approval/invitation/accounting transitions. No Python application service, marketplace, escrow or orchestration framework is introduced. Python is used only for a standard-library test harness.

The model has no authority. Database membership controls visibility, not a browser role label. RLS covers records and Storage objects; authenticated Postgres Changes uses table RLS. Hosted Supabase Realtime isolation has been verified with authenticated client/professional fixtures. The browser waits for session/token initialisation and backend subscription readiness before showing a connected status, refreshes when connecting/reconnecting, and ignores callbacks from disposed effects. Shared copies contain only selected reviewed text and a shared audit event. They contain no original private conversation reference. No private activity enters shared audit views.

Signup stores a default profile type and an active account context. The account menu switches the active context, which filters the dashboard and supplies the role for new engagements. Accepting an invitation switches the context to the accepted membership role. The database verifies that creation uses the saved active role. Switching never changes existing memberships, private-agent ownership, approval authority or invitation roles. Direct links to an existing engagement continue to use its membership role.

Messages and submitted scope records are append-only: no client UPDATE/DELETE privileges exist. Edit/redaction tools are not yet implemented. Evidence should cite immutable message IDs and version IDs. Submitted versions use a per-engagement lock; approvals cannot accept a superseded submission. Accepted agreement references survive newer proposals.

Shared and private discussion files are selected in the message composer. The server uploads a pending object, then atomically creates the human message and marks its attachment ready with that message as its source. Authenticated callers cannot confirm a standalone attachment. Pending objects and metadata are visible only to their uploader; failed pending uploads do not appear in Discussion or Files. A failed confirmation is cleaned up when its status can be verified.

Milestone-local approval and history are in Milestones. Review eligibility and privacy remain enforced in the database.

Invitations last seven days, bind to a verified email and a database-selected vacant role, use hashed 256-bit tokens, and record acceptance. A live pending invitation blocks a second one; the creator must revoke it or wait for expiry before inviting another address. The database checks this under the engagement lock, and the Discussion form is hidden while an invite is pending. Verified recipients see pending invitations on their dashboard regardless of active profile role. This RPC returns only ID, title, role and expiry for the recipient's email; it never exposes tokens or engagement content. Dashboard and email-link acceptance share the same locked email/status/single-use checks. Tokens appear in links, so production must use HTTPS, avoid request-URL logging, and never include third-party resources on invitation pages. One user cannot occupy both parties.

Files are private; shared queries do not return private metadata. Only supported content types up to 20 MB are accepted. Files are force-downloaded using 60-second signed URLs. PDF/image signatures and UTF-8 text are validated server-side, and filenames have path/control/bidi characters removed. This is a basic signature check, not full format validation or malware scanning. Failed upload metadata is removed when no object exists. Completed downloads require explicit upload confirmation; an interrupted request may leave a pending record, which is labelled as unconfirmed. Confirmed uploads create one visibility-scoped source message, with no private event sent to the counterparty. Source links and formal submission links are shown in Files. Name/type filters and bounded plain-text previews operate only on the selected authorised context. TXT/CSV decoding stores immutable, SHA-256-versioned text (up to 50,000 characters), with partial/error states. PDF/image analysis, malware scanning, actual transfer progress and scheduled abandoned-upload cleanup remain pending.

## Credit and failure billing policy

The customer unit is a Workspace token: 10 tokens = $1 of AI usage value. One internal USD nanodollar equals one hundred-millionth of a token, so existing balances convert exactly; the $5 starter grant is 50 tokens. Provider rates, metering costs and pricing snapshots are restricted to server-only access. Customer-scoped usage exposes token charges and status without provider economics.

Amounts use bigint USD nanodollars. A starter grant is exactly 5,000,000,000 nanodollars. Account rows are locked for reservations; unique operation keys prevent duplicate accounting. Promotional/purchased lots conserve available + reserved + spent + refunded + admin-removed units. Reservations allocate promotional credits first and retain their source through settlement, release and correction. Ledger and metering records are append-only to application callers. A verified, allowlisted admin can grant or revoke available promotional demo units through a service-only transactional RPC, with actor, reason and before/after audit. Reserved and purchased units cannot be revoked by this control. At least $5 of admin-granted shared credits activates a pending hackathon engagement. Real purchase verification remains implemented as a service-only primitive; public credit checkout is deferred until after the hackathon.

Customer charge is actual attributable provider cost × 2, using immutable per-event model rates and cached-token quantities without per-operation cent rounding. Internal application errors and recovery retries are platform-funded. Provider failures without usable output incur no customer charge. A usable partial result requires the initiating human's explicit Keep-and-charge decision; discard is free. Unknown attribution and reservation overruns are platform-funded. Known expenses and uncertain provider response IDs remain in private/scoped accounting records for reconciliation. No real AI request has been made; see AI.md.

Partial offers expire after 24 hours. The authenticated maintenance endpoint releases expired work and clears unpublished partial results; it requires a deployment scheduler that is not yet configured. Full usage corrections return units to their original promotional/purchased lots without overwriting historical charges. Service-only aggregate promotional spending supports basic monitoring; no identity verification or device fingerprinting is added.

Versioned credit policy offers $5/$10/$25 top-ups. Purchased credits have no invented expiration. A purchaser can explicitly request a whole-cent refund of unused purchased units; those units are reserved pending review. Only a verified provider refund permits completion; rejected requests release the hold. Sub-cent unused units remain available. Promotional units are non-transferable/non-withdrawable and cannot be refunded. These primitives do not execute PayPal refunds or purchases. Credit sales and usage at 2× attributable provider cost are the planned platform revenue source.

Professional payments will be direct-to-seller at the accepted agreement amount, with no Workspace commission. No custody or escrow. PayPal processing fees are separate and provider-derived; the eventual seller integration must verify which account bears them.

## Reviews

The agreed policy requires a genuinely accepted agreement before a completed or cancelled engagement can open a review window. An invitation, brief discussion or unaccepted proposal never qualifies. Publish after both submit or 14 days, disclose cancellation context, freeze submissions and support replies/reports. The database, RLS, public projection and UI enforce this policy; see the implementation details below.

## Discussion and notifications

Replies reference a root message in the same engagement and exact visibility. Shared human messages automatically notify the other party; the composer has no mention controls. Historical mention records and their permission checks remain intact. Notifications contain shared record references, not message excerpts or private activity. RLS restricts notices and read cursors to their owner. A focused, visible latest Discussion page marks messages read when its end enters the viewport; private contexts, background tabs, older pages and evidence-only views do not advance the shared cursor. The monotonic read transaction also clears that reader's message/reply/legacy-mention notifications through the same cutoff, without clearing later messages or other event types. Read cursors are not counterparty-visible read receipts. Notifications also cover scope approvals/acceptance, invitation acceptance, delivery/review, meeting responses and mutual review publication. Counters currently show the loaded recent 50 records; notification pagination and instant approval notification refresh remain pending.

## Milestones, delivery and meetings

A structured milestone plan is part of each immutable scope JSON version, materialised into relational tasks/dependencies. Invalid dates, cyclic/foreign dependencies and allocations exceeding the agreement price are rejected transactionally. Date-only schedules are separate from meeting instants. Editing a schedule submits a complete new scope version; both parties approve that exact version. Progress and delivery records retain their original task/version references after later agreements. Facts do not silently migrate to a new commitment; older schedules/submissions remain visible in history.

Only the accepted task's owner can report progress. Only the professional can formally submit delivery, and only the client can accept/request changes against its criteria. Shared ready attachments from that engagement are allowed; private/cross-project files are rejected. Delivery reviews are immutable; revised work needs a new numbered submission. Reporting 100% progress does not imply acceptance or payment.

The professional can record a payment request only against the exact current accepted agreement. The database calculates its USD amount from a payable milestone or the agreement price less allocated milestone amounts, with one request per item/version. A new accepted revision marks earlier unpaid requests superseded without rewriting their historical amount or reference. The client sees a shared notification and request history. This is a claim for discussion, not a charge, payment confirmation, escrow balance or agent authority. PayPal checkout and provider reconciliation remain unimplemented.

Both parties can open and respond to a shared concern. Full positions are copied into shared Discussion so the neutral project agent can cite them when invoked. Each party acknowledges resolution independently; two acknowledgements close the case. This records shared understanding only and never changes scope, payment, legal rights or engagement status. Invitation revocation is explicit and audit-recorded; a revoked link cannot be accepted.

Meetings have stable IDs and immutable proposals. A proposer records their own acceptance; the other party accepts/declines the same current version. A new time does not replace a previously confirmed time until both accept it. Responses, changes and notes create shared Discussion events. Cancellation checks the current version and records a reason. UTC instants plus IANA timezone are stored; nonexistent DST times are rejected and repeated times require an explicit earlier/later choice. Internal clash warnings describe only the viewer's known authorised meetings. ICS uses stable UID, increasing sequence, UTC timestamps, safe escaping and UTF-8 folding. Downloads require membership and have no-store headers. No emailed invitation, external free/busy sync, hosting or transcription exists.

## Reputation implementation and limits

Completion requires both parties' confirmations against the current accepted agreement. Either party may explicitly cancel; cancellation does not decide liability, refunds or settlement. Closed engagements cannot be reactivated by approving an old proposal. Only closing an engagement with an accepted agreement opens the 14-day review window. Invitations/discussion/unaccepted proposals do not qualify.

Submitted feedback is frozen. RLS exposes unpublished feedback only to its author; the subject cannot read its body/ratings through APIs. Publication occurs when both submit or the deadline passes, with deadline visibility enforced in SQL even without a scheduled job. Participants can then read both reviews. Anonymous/public access goes through `public_profile`, which deliberately projects opted-in identity fields, written role-specific feedback, completion facts, client-approved portfolio and badge criteria. Base profile/review tables are not anonymously readable. Private engagement identifiers, title, price, files and discussion are excluded. Author identity is linked only when that author's profile is public.

The reviewed party can submit a frozen reply. Verified users can submit policy reports; reports are owner-only. Subjects cannot remove reviews. Trusted platform staff may call service-only `moderate_review` with a recorded decision/reason after reviewing a report; there is no automated moderation decision or staff console. Valid criticism is not grounds for unilateral removal. Text corrections require a documented staff process; no silent self-edit is offered.

A portfolio example is immutable text plus an HTTPS link, proposed by the professional. Public display requires the client's exact-example permission, the professional's publication flag and an opted-in professional profile. The client can revoke permission. File publication is not automatic. Company identity currently has one authorised account representative per party.

Demo-labelled engagements are excluded from public reviews, completion counts, portfolios and badges. The initial badge records a mutual completion only and publishes its criteria. No quality, identity or fraud-free verification is claimed. Two accounts can manufacture activity; accepted agreements, payments and completed tasks alone do not prove work quality. Initial limits are verified accounts, genuine membership and accepted-agreement eligibility, unique mutual reviews, frozen feedback, reports and monitoring; stronger anti-manipulation controls require observed evidence. Archive transitions, a full staff console, repeat-engagement statistics and concerns/mediation records remain later work.

## Professional payment ledger

Payments holds shared request and sandbox receipt history. Milestones display their own payment state, based on verified captures less completed refunds across the stable milestone ID, including older accepted versions. Historical payment requests keep original task/set references. Professional hourly/other requests and client bonuses are independent of the agreement price and require explicit client PayPal approval. Neither a request, a provider return URL nor a pending capture is treated as payment.

`payment_transactions`, `payment_refunds` and the append-only `payment_ledger` have engagement RLS and no authenticated write privileges. `paypal_sellers` is owner-readable only; verification is performed using server-only provider credentials and stored tracking IDs. Only service RPCs record provider receipts after server verification. Ledger totals use fixed-point cents and completed events, and do not include AI token purchases or inferred PayPal processing fees. CSV is member-only, no-store, bounded by a stable upper cursor and paginated past the API's default row limit; spreadsheet formulas in descriptions are escaped.

Capture checks client identity, exact stored request/order/recipient/amount/currency and current milestone authority. A short database capture reservation prevents an accepted revision racing an uncertain charge. Refunds require the original seller's explicit action and original capture; concurrent reservations cannot exceed the remaining captured amount. Duplicate/delayed events do not duplicate or undo completed receipts. Browser callbacks only offer an authenticated POST completion action. Webhooks are verified against the configured webhook ID through PayPal, then authoritative order/refund resources are fetched before reconciliation. Superseded, uncaptured checkouts release their local reservations and cannot be captured or revived by a delayed pending event. A late verified capture remains in history and is included in the current balance check. Live endpoints are not supported. Actual provider-backed capture/refund/webhook checks remain pending configuration; see PROVIDERS.md.
